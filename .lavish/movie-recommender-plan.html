An Amazon-style suggestion engine over 70 movies and 806 users. Pick a few movies you like, get ranked recommendations with a plain-language reason for each. Nuxt 4 + Vuetify, a server-side recommender, free movie metadata, and end-to-end tests only.

02Free movie data

The file gives only titles. For a credible UI we want posters, synopsis, genres and director. We resolve this once at build time into a committed catalog.json, so the running app has no third-party dependency and e2e tests are deterministic.

Decided: scripts/build-catalog.ts reads TMDB_API_KEY from .env (already gitignored; we add a committed .env.example). It resolves each of the 70 titles via TMDB title + year search and writes server/assets/catalog.json with title, year, overview, genres, TMDB poster path and a blurhash. The key is only needed to regenerate the catalog; the deployed app and the e2e tests never need it. Unmatched titles fail the script with a report, and an override map handles known mismatches (e.g. “Postino, Il”).

03How we recommend

Item-based collaborative filtering. For each movie pair, count users who liked both (co-likes). To score a candidate, sum its similarity to every movie the visitor picked. It fits a binary “liked” signal, runs instantly on 70 movies, and every result can explain itself (“because you liked A and B”).

I prototyped it against the real data with a leave-one-out test (hide one liked movie per user, check whether it appears in the top 5; 684 users with ≥5 likes). The result changes the design:

Popularity damping αHit@5Toy Story + Aladdin + Lion King →Reading
— (most-popular baseline)0.496Star Wars, Fargo, …Same list for everyone. Not a recommender.
0.50 (plain cosine)0.532Empire Strikes Back, Jurassic Park, Raiders, Star WarsBarely beats baseline. Disney fans get Star Wars.
0.65 candidate default0.482Jurassic Park, Apollo 13, Forrest Gump, EmpireSlightly less accurate, noticeably more tailored.
0.800.393Jurassic Park, Top Gun, Sound of Music, Apollo 13Tailored but drifting; niche titles creep in.
1.000.045Free Willy 2, Aristocats, Doom GenerationOnly rarities. Unusable.
Honest read: with 70 mostly-blockbuster titles, accuracy and “feels personal” pull against each other and no setting is a clear win. I recommend exposing α as a documented server constant (default ~0.6, tuned by the same leave-one-out metric) rather than a UI slider. The offline eval prototype becomes a repeatable scripts/evaluate.ts so the choice is defensible. Note the free-willy-style rarities in the data (7–11 likes) make long-tail scores noisy; we ignore similarity from pairs with fewer than N co-likes.
  • Cold start: zero picks → return the most-liked movies, labelled “Popular”, never an empty state.
  • Explanations: each result carries its top 2–3 contributing picks and a normalised 0–1 match score.
  • Exclusions: picked movies are never recommended; ties break by popularity then id so output is deterministic (needed for stable e2e assertions).

04Architecture

flowchart TD B[Browser page index.vue] -->|useFetch GET| M[api/movies.get.ts] B -->|POST| R[api/recommendations.post.ts] R -->|validate body| V[utils/schemas.ts zod] R --> E[utils/recommender.ts pure engine] M --> C[utils/catalog.ts] E --> D[(assets/movies.json)] C --> K[(assets/catalog.json)] S[scripts/build-catalog.ts build time only] -.->|TMDB API plus blurhash| K B -.->|poster image| T[image.tmdb.org]

The engine builds its co-like matrix once per server process (module-level lazy singleton) and answers each request in microseconds. The shared Movie / Recommendation types live in shared/types (Nuxt 4 convention) so client and server cannot drift.

API contract

GET /api/movies
→ 200 [{ id, title, year, posterUrl,
         overview, genres[] }]   // sorted by title
POST /api/recommendations
{ "liked": [20, 59, 60], "limit": 10 }
→ 200 { source: "personalized" | "popular",
        items: [{ movie, score,
                  because: [{id,title}] }] }
→ 400 unknown ids / empty-after-dedupe / limit out of range
→ 422 body fails schema

POST (not GET) avoids URL length limits, but the page state still lives in the URL as ?liked=20,59,60 so results are shareable, SSR-rendered, and survive refresh.

  • Components: MovieSearch (v-autocomplete, keyboard accessible), LikedChips, MovieCard, RecommendationGrid, RecommendationEmpty/Error states, AppShell layout, and AppFooter carrying the TMDB logo attribution: official logo (downloaded from that page into public/) linking to themoviedb.org, plus the required line “This product uses the TMDB API but is not endorsed or certified by TMDB.”
  • State: a useLikedMovies() composable backed by the route query; useRecommendations() wraps useFetch with a reactive key so it re-fetches (debounced) and is SSR-safe. No Pinia needed.
  • Posters: remote from the TMDB image CDN, never copied into the repo. A PosterImage component shows the movie’s blurhash (decoded to a small canvas) instantly, then fades the real poster in when it loads; it keeps a fixed 2:3 box so there is no layout shift, and falls back to the blurhash with a title overlay if the image errors. Blurhashes are computed once by the catalog script (it downloads each poster a single time to hash it, then discards it).
  • Quality bars: responsive down to 360px, dark mode via Vuetify theme, data-testid hooks, alt text on posters, strings in the i18n en locale rather than hard-coded.

Look and feel: rusticit.com

  • Palette from its CSS: charcoal #0e152e and off-white surfaces, purple #4a4ac0 / #6f6fbe primary, cyan #07c6ff as the sparing accent. Both light and dark themes, following the site’s dark-class convention and system preference.
  • Type: Rubik for headings, Inter for body (both are variable fonts the site already ships; we self-host via @nuxt/fonts).
  • Floating pill header with blurred backdrop, rounded corners, thin low-contrast borders. Implemented as a Vuetify theme (colors, defaults, rounded) so components inherit it rather than being overridden with CSS.
  • Product name “Movies RusticIT”, linking back to rusticit.com. Footer has the TMDB attribution.

Analytics: Umami

  • Same Umami Cloud account as rusticit.com, but its own website entry so movies traffic does not mix into the main site’s numbers. You create it in Umami and give me the website id; I will not reuse the rusticit.com id.
  • Loaded from cloud.umami.is/script.js via Nuxt app.head with defer, only when NUXT_PUBLIC_UMAMI_WEBSITE_ID is set (so dev and tests stay clean). Umami is cookieless, so no consent banner is needed.
  • A small useAnalytics() composable wraps window.umami?.track (safe no-op if blocked). Events: movie-picked, movie-removed, recommendations-shown (pick count, source), recommendation-clicked. Payloads carry movie ids only, never anything personal.
  • Add .env.example entry and set the variable in Netlify.

09Risks

Quality

Weak personalization

Only +3.6 points of hit@5 over “just show popular”. Mitigation: damping, min co-like threshold, honest explanation text, documented eval. We won’t oversell it.

Data

Title matching

MovieLens titles (“Postino, Il”, “ID4”, “Se7en”) can mismatch TMDB. Mitigation: normaliser plus an explicit override map; the script fails loudly on unmatched ids.

Legal

Poster and API terms

TMDB requires the logo attribution in the footer (planned, with an e2e check) and non-commercial use. A display-only demo on movies.rusticit.com fits, but any monetisation would need a commercial TMDB agreement.

Process

E2E-only is slower

Browser tests cost more than unit tests. Mitigation: heavy logic coverage goes through the API layer ($fetch, fast), browser tests stay focused on UI behaviour.
