User profiles and a stacked-avatar switcher

Four demo viewers, each with a name, an avatar, a language preference and their real liked movies from movies.json. A stack of avatars in the top right switches the whole app to another viewer. i18n itself is out of scope here, so this plan only stores the language choice.

One correction to the brief: server/assets/movies.json holds 806 users (user_id 1–806, array index = id − 1), not 4. There are four avatars, so the plan makes profiles from the first four users and leaves the other 802 untouched. Which four is decision D4 below. Every liked id for users 1–4 exists in the 70-movie catalog.

    3What "clean context" means

    Today the page is a pure function of the URL: useLikedMovies reads ?liked=, and useRecommendations keys its fetch on the settled picks (recommendations:20,59). The plan keeps that property by putting the active viewer in the URL too, so a switch is one navigation and nothing can be left over from the previous viewer.

    Reset on every switch

    • Picked movies: the URL liked is replaced by the new viewer's likes, so edits made as the previous viewer do not leak.
    • Search box text and open dropdown (MovieSearch remounts via :key="profile.id").
    • The "ignored ids" warning, error and retry state of the recommendations.
    • In-flight recommendation request (the debounced settled picks are re-seeded, not carried over).
    • Scroll position.

    Rules for the URL

    • ?user= missing → middleware picks the cookie's viewer, else the first profile, and redirects with user and their likes filled in.
    • ?user=sam without liked means "no picks" (popular fallback), not "reseed". Seeding only happens when user is missing, so removing the last chip never loops.
    • Unknown user → treated as missing (same graceful drop as invalid liked ids today).
    • A "Reset to my likes" button re-applies the profile's likes after edits.

    6Risks and interactions

    • Shared links now carry two params. That is intended: the recipient sees the same viewer and picks. Cost: longer URLs (Dale's 53 ids is about 150 characters).
    • Movie detail page plan (/movies/[id], card → page transition): every link and the back link must preserve user (and liked), or navigating back would reseed. Noted in that plan's build, not changed here.
    • PR #2 (theme toggle) touches the same app bar. Whichever lands second resolves a small conflict in AppShell.vue.
    • No security, by design. Anyone can be anyone; the cookie is only a convenience. The README should say this is a proof of concept.
    • Privacy invariant relaxed on purpose. The API used to expose no per-user likes. It now exposes four fabricated profiles' likes; the 802 other users remain internal, and the contract test guards that.
    • Recommender not touched. It still takes liked: number[]. Dataset users 1–4 are also training data for the model, so these viewers' own likes are in the co-occurrence counts. That slightly flatters their recommendations; the leave-one-out eval is unaffected.
